# Архитектура

Обновлён: 18.09.2026
Версия схемы данных: 1

## Стек

- **Vite + React + TypeScript**, `strict` и `noUncheckedIndexedAccess`. Проект идёт через много сессий, и без типов модель расползётся между ними
- Роутинг через хеш (`#/today`), `HashRouter` из `react-router-dom` — на GitHub Pages обычные пути дают 404 при обновлении страницы
- Сайт живёт по `/Trapeza/`, а не в корне домена: `base` в `vite.config.ts` равен имени репозитория (Р-10). С ним же согласованы `start_url`, `scope`, `id` манифеста, пути иконок и `navigateFallback`. Неверный `base` даёт зелёную сборку и белую страницу
- Стили обычным CSS
- Хранилище на устройстве — IndexedDB
- Service worker свой, собирается `injectManifest` — иначе в него не положить код напоминаний. Точка входа — `src/sw.ts`, три строки: кеш, работа без сети и автообновление — `startWorker` ядра, своё — тема напоминания (Р-48)
- **Ядро — `FamilyCore`, подмодулем в `src/shared`** (Р-45…Р-52). Сборка — фабрикой ядра `familyVite`, `tsconfig` — `extends` ядра, иконки — `writeIcons` ядра со своими фигурами
- В манифесте — `shortcuts`: «Записать» по долгому тапу на иконке (Р-04)
- Бэкенда нет. Платформа — PWA; обёртка в APK — запасной путь с поводом (Р-04)

## Два репозитория

| Репозиторий | Что внутри | Видимость |
|---|---|---|
| `Trapeza` | исходники, сборка, GitHub Pages | публичный |
| `TrapezaData` | JSON-файлы с записями | приватный |

Pages для приватного репозитория требуют платного тарифа, поэтому код публичный. Секретов в нём нет по определению. Токен вводится руками в настройках и живёт только в браузере.

## Модель данных

Две категории сущностей: **справочники** (из чего записываем) и **записи** (что съедено).

### Общая часть

```ts
type Base = {
  id: string          // ULID, генерируется локально; у справочников — из названия (Р-12)
  updatedAt: string   // ISO 8601, время последнего изменения записи
  deleted?: boolean   // метка удаления, не вычищается никогда
}
```

Та же `Base`, что в «Дневниках» и «Делу Время», — чтобы метаприложение слило ленты без переделок (Р-06). С переводом на ядро это буквально один тип — `shared/core/model.ts`, договор семьи (Р-51).

### Справочники

```ts
// Категория: Каши, Супы особые, Мясное, Сладости, Сладкие напитки, Компот… (Р-15)
// id — `cat:<название>` (Р-12)
type Category = Base & {
  name: string
  order: number                // порядок в итогах дня и недели
  group?: string               // укрупнение для сводок: «Каши», «Пироги и сладости», «Напитки» (Р-15)
  archived?: boolean
  movedTo?: string             // у надгробия: куда слита или перенесена (Р-12)
}

// Блюдо или продукт: «Гречка», «Борщ», «Компот», «Сырок» — одна структура (Р-02, Р-07)
// id — `dish:<название>` (Р-12)
type Dish = Base & {
  name: string
  categoryId?: string          // нет — «без категории»; итоги называют, сколько таких (Р-02)
  portionGrams?: number        // вес порции по умолчанию
  kcal100?: number             // ккал на 100 г — справочно (Р-03)
  kcalPortion?: number         // ккал на порцию — когда граммы не известны: «кофе с молоком»
  recipe?: string              // текст по заготовке (Р-39); необязательное поле — без миграции
  archived?: boolean
  movedTo?: string             // у надгробия: куда слито (Р-12)
}

// Шаблон приёма — «обычный завтрак» — или дня — «обычный день». Заводится из записанного (Р-08, Р-28)
type Template = Base & {
  name: string
  meal?: Meal                  // есть — шаблон приёма; нет — шаблон дня, приём у каждого блюда
  items: { dishId: string; meal?: Meal; portions?: number; grams?: number }[]
  order: number                // порядок внутри своего вида: шаблоны дня, шаблоны одного приёма
}

// Норма недели над набором категорий: «Сладкое — не больше 4 дней» (Р-13)
type Norm = Base & {
  name: string
  categoryIds: string[]
  minDays?: number             // дней с записью — не меньше
  maxDays?: number             // дней с записью — не больше
  since?: string               // YYYY-MM-DD; нет — вся история (отступление от «Делу Время», Р-13)
  order: number
}
```

### Записи

```ts
// Съеденное: одно блюдо в одном приёме одного дня (Р-11)
type Intake = Base & {
  date: string                 // YYYY-MM-DD, день еды, не день ввода
  meal: Meal
  dishId: string
  portions?: number            // нет — 1; дробные законны: «полпорции»
  grams?: number               // правка порции граммами; есть — главнее portions
  at?: string                  // ЧЧ:ММ, по желанию (Р-14)
  note?: string                // «в кафе», «изжога» (Р-05, Р-15)
  refs?: string[]
}

type Meal = 'breakfast' | 'lunch' | 'dinner' | 'snack'

// Вид записи. Одно значение — ровно то, что описано выше.
type RecordKind = 'intake'
```

### Заметки по модели

- **Одна запись на блюдо, а не на приём** (Р-11). Итоги по категориям и частота блюда в приёме считаются без разбора состава; слияние по записи не склеивает правки двух устройств в один приём
- **Приём при записи ставится по часам устройства**, границы — настройка устройства `mealHours`: по умолчанию завтрак до 13:00, обед до 18:00, дальше ужин. Перекус — только явно: по часам между обедом и ужином всё стало бы обедом или ужином. `at` от приёма не зависит (Р-14)
- **Калорийность записи — чистая функция, с тестами.** Есть `grams`: `grams × kcal100 / 100`; без `kcal100` — `grams / portionGrams × kcalPortion`. Нет `grams`: `portions × ккал порции`, где ккал порции — `kcalPortion` или `portionGrams × kcal100 / 100`. Не хватает данных — запись вне суммы, и итог называет, сколько таких: «1 850 ккал по 9 из 11 записей» (Р-01)
- **Id категорий и блюд — из названия** (Р-12): `cat:<название>`, `dish:<название>`, регистр, «ё» и лишние пробелы не в счёт — то же правило, что у поиска. Одноимённые после прихода данных — с сервера или из файла — сливаются сами: остаётся id, совпадающий с названием, иначе наименьший; содержимое — от поздней правки; записи, шаблоны и нормы переходят к оставшейся. Надгробие хранит `movedTo`, и запись, приехавшая к нему позже, уходит по цепочке. Удаление справочника с записями — только переносом, тоже через `movedTo`. Образец — `modules/time/categories.ts` «Делу Время» (их Р-22, Р-29); здесь это код модуля `food`, не ядра
- **Записи, шаблоны и нормы — ULID.** Справочники — два исключения из «id — ULID»
- **Норма** (Р-13): «раз» — день, в котором есть запись хоть одной категории нормы. Категория может стоять в нескольких нормах. История — полные недели с понедельника не раньше `since`; «выполнена в N из M» — с трёх недель в счёт, как в «Делу Время» (их Р-53, Р-56). **`since` необязательно, и без него — вся история:** иначе импорт февраля–марта (Р-09) не дал бы нормам ничего. **Неделя в счёт — когда её исход ясен** (Р-24): день без записей неизвестен; «не больше» провалена при `d > max`, выполнена при `d + u ≤ max`, «не меньше» — зеркально; неясные недели не в счёт и названы числом. Отклик норм без цвета (Р-23). Расчёт — `modules/food/norms.ts`, итоги недели — `modules/food/week.ts`; экран — `screens/Week.tsx`, `#/week?w=` (Р-25)
- **Порядок по частоте** (Р-08, Р-17): блюда приёма упорядочены по числу дней, в которые блюдо было в этом приёме за скользящий месяц до просматриваемого дня, сам день не в счёт; при равенстве — по всей истории до него, затем по названию; окно — константа модуля. «Как вчера» — копия последнего такого же приёма до просматриваемого дня, тоже без дублей. Шаблон применяется без дублей: блюдо, уже стоящее в этом приёме этого дня, второй раз не ставится
- **Шаблон** (Р-28): приёма или дня — одна запись `Template`, у шаблона дня приём у каждого блюда; инвариант держит `modules/food/templates.ts`. Шаблон дня на сегодняшнем дне пишет только начавшиеся приёмы по `mealHours`, перекус — нет; на прошлом — целиком
- **«Как обычно?»** (Р-29): сегодня — основные приёмы до текущего без записей, вчера — все три; шаблон приёма, иначе приём из шаблона дня, иначе блюда, бывшие хотя бы в половине последних двадцати таких приёмов. «Не было» — настройка устройства `usualSkipped`. Расчёт — `modules/food/usual.ts`
- **Напоминание** (Р-30): сегодня ни одной записи или вчера без записи завтрака, обеда или ужина без отметки «Не было». Расчёт — `modules/food/remind.ts`, механика — `notify.ts` и `sw.ts`
- **Выбор блюда в приёме** (Р-26): «Частые» по частоте Р-17, ниже — все блюда по категориям свёрнутыми, внутри — по частоте. Ручного порядка блюд нет. Поиск не нашёл ни одного живого блюда — «Завести „<запрос>“ и записать»: блюдо без категории с id из названия и запись одним тапом (Р-36). Запрос — название блюда в архиве: «Вернуть „<название>“ из архива и записать», второе не заводится; совпал с надгробием — оно оживает (Р-12)
- **Тап по блюду, уже стоящему в приёме этого дня, прибавляет порцию к той же записи**, а не заводит вторую: одинаковые блюда приёма — одна запись с `portions`, тот же естественный ключ, что у импорта. Запись в граммах так не правится — только формой. Прошлый день на «Сегодня» — адрес `?day=ГГГГ-ММ-ДД`, без параметра — сегодня
- **Итог дня — в порциях** (Р-18): запись с граммами — `grams / portionGrams`, без `portionGrams` — одна порция, и итог называет, сколько таких. Правка порций — шагом ½ и полем
- **Рецепт** (Р-07, Р-39) — необязательное поле блюда, один текст. Ссылок на другие блюда нет: ингредиенты, выход и шаги — строки текста. Пустое поле заполняется заготовкой («Порций», «Время», «Ингредиенты», «Как готовить», «Заметки») — константа в `modules/food/recipe.ts`, оттуда же промпт для ИИ. Калорийность из рецепта не считается: она остаётся введённой (Р-38)
- **Стартовых категорий и блюд в коде нет** (Р-15). Приходят импортом: код публичный и уезжает к другу
- **`refs` — связи между записями** и, позже, между приложениями семьи. Строка ссылки начинается с вида записи: `intake:<id>`

## Раскладка данных в репозитории

```
meta.json                 { schemaVersion }
categories.json           категории
dishes.json               блюда и продукты
templates.json            шаблоны приёмов
norms.json                нормы недели
intake/2026-02.json       записи за месяц
intake/undated.json       запись с испорченной датой
README.md                 что здесь лежит; кладётся приложением, если его нет
```

Месяц записи берётся по `date`. Испорченная дата — запись уезжает в `intake/undated.json`: терять её из-за одной кривой строки нельзя. У `Intake` дата обязательна, поэтому законных записей без даты нет.

Нарезка по месяцам, а не по годам: обычный день — 6–8 записей, месячный файл — порядка 50 КБ, годовой к декабрю — около 600 КБ и уезжал бы целиком с каждым тапом. Закрытые месяцы не переписываются, пока в них ничего не правят. Раскладка — поле `places` в `src/app/config.ts`, единственное место, где она известна; файлы по ней собирает ядро (Р-47).

## Синхронизация

**Принцип: local-first.** Запись сохраняется на устройстве и отражается на экране до всякой сети. Синхронизация — фоновый процесс, который может отставать или падать, не ломая работу.

Механика — ядра `FamilyCore` (`shared/core/sync.ts`), родом из «Делу Время» (Р-06), вместе с их нарезкой по месяцам, исправлением `syncNow` (проход отпускается и тогда, когда синхронизация не настроена) и `README.md`, который кладётся проходом, если его нет в дереве. Шаги прохода:

1. Запись падает в IndexedDB, экран обновляется мгновенно
2. Изменённые записи помечаются грязными — это признак «есть что отправлять», а не список файлов
3. Через пять секунд после последнего действия — проход. Также при открытии, при возврате вкладки из фона и при возврате сети
4. Читаем голову ветки и дерево файлов — два запроса. Скачиваем только файлы с разошедшимся отпечатком
5. Сливаем в базу, пересобираем дерево из базы целиком, отправляем разошедшиеся **одним коммитом**
6. Ветка ушла вперёд → пауза, перечитать, слить заново. Три попытки, потом откладываем на минуту
7. **Сначала влить чужое, потом отправить своё.** Любая ошибка чтения обрывает проход до записи

Репозиторий без единого коммита Git Data API не обслуживает: первый файл кладётся через Contents API.

### Правило слияния

**Для каждой записи по `id` побеждает версия с более поздним `updatedAt`.** По записи, а не по файлу целиком — иначе запись с телефона затрёт запись с компьютера. Удалённые остаются надгробиями навсегда: вычистишь — второе устройство воскресит. После слияния — слияние одноимённых справочников (Р-12).

### Файл-копия

Кнопкой в «Настройках» скачивается один файл-слепок, а не раскладка выше:

```
{ schemaVersion, exportedAt, data: { <хранилище>: [записи] } }
```

Все синхронизируемые хранилища вместе с надгробиями. `settings` не входит — там токен. Загрузка сливается общим правилом. Форма проверяется до записи, файл чужой схемы отвергается целиком. Делимся `.txt` с тем же содержимым: Chrome на Android не отдаёт `.json` в системное «Поделиться».

### Импорт записей

Второй вход — для стартового списка блюд и истории таблицы (Р-03, Р-09). Слепок сюда не принимается, у него свой вход.

```
{ "format": "trapeza-import", "version": 1,
  "categories": [...], "dishes": [...], "intake": [...] }
```

Без `id` и `updatedAt`, ссылки по названиям: категория и блюдо ищутся по имени без учёта регистра, «ё» и пробелов; недостающие заводятся с id из названия (Р-12).

- **Раздел `categories`** — `name`, `group`: группы из листа итогов (Р-15)
- **Раздел `dishes`** — `name`, `category`, `portionGrams`, `kcal100`, `kcalPortion`; всё, кроме названия, необязательно
- **Раздел `intake`** — `date` (только днём), `meal`, `dish`, `portions`, `grams`, `at`, `note`
- Каждое поле проверяется; кривая запись в базу не попадает и называется с причиной
- До записи — сводка: что добавится, что уже есть, что не разобрано. Пишется только по кнопке
- **Только добавляет.** Совпавшее по естественному ключу пропускается. Ключи: категория и блюдо — название; запись — дата, приём и блюдо. Отсюда граница: два одинаковых блюда в одном приёме одного дня — одна строка с `portions`, как сумма порций в ячейке таблицы
- JSON принимается и в блоке ` ```json ` с текстом вокруг — так его отдаёт ИИ

Поля и пример каждого раздела описаны в `modules/food/import.ts`; из тех же описаний собирается промпт для ИИ, и тест прогоняет примеры из промпта через собственную проверку. Примеры выдуманные: промпт уезжает к каждому.

Разделы разбираются по порядку — категории, блюда, записи — и каждый видит заведённое предыдущими: блюдо из того же файла не заводит свою категорию второй раз. Запись, повторившая естественный ключ внутри одного файла, — в отчёт, а не в пропуск: молча потерялись бы порции. Промпт запрещает ИИ выдумывать записи; оценка разрешена только в полях, где так и сказано, — порция и калорийность блюда (Р-03).

История таблицы переводится в этот формат разовым скриптом вне приложения: цвета заливки ИИ из текста не видит (Р-09); легенда и неясные ячейки — Р-19. Файл — личные данные, лежит в `/seed/` под `.gitignore`; тест настоящих данных читает его, без файла пропускается.

## Локальное хранилище

IndexedDB, не localStorage: у второго лимит около 5 МБ и синхронный API, который подвесит интерфейс на импорте.

База называется `trapeza`. Имя обязано отличаться от `dnevniki` и `deluvremya`: все три приложения живут на одном origin `goigolden88.github.io`, а IndexedDB общая на origin и различается только именем. Кеши service worker разведены сами — workbox вписывает scope в имя кеша.

Синхронизируемые хранилища — `categories`, `dishes`, `templates`, `norms`, `intake`: имена совпадают с раскладкой в репозитории. **Все пять — в `v1Stores` конфига с первого дня:** шаблоны и нормы известны сейчас, и заводить их миграцией потом незачем. Локальные — `meta`, `settings`, `dirty`. Имена лежат в базе на устройствах и не меняются никогда. Индекс сверх `updatedAt` — у `intake` по `date`. Всё это — поля `AppConfig` в `src/app/config.ts`, значения те же, что до перевода на ядро; проверка — `app/config.test.ts`.

Настройки хранятся отдельно и **не синхронизируются**: в них токен, а «когда я в последний раз синхронизировался» у каждого устройства своё.

| Ключ | Что лежит |
|---|---|
| `syncEnabled` | включена ли синхронизация. По умолчанию нет |
| `syncRepo` | `владелец/репозиторий` данных |
| `syncToken` | fine-grained токен. В выгрузку не попадает никогда |
| `syncBranch` | ветка, по умолчанию `main` |
| `syncTokenExpires` | когда истекает токен |
| `syncLastAt`, `syncLastCommit`, `syncTree` | состояние последнего успешного прохода |
| `lastExportAt` | когда в последний раз забирали копию файлом |
| `mealHours` | границы приёмов `{ lunch, dinner }` — час начала обеда и ужина; нет — 13 и 18 (Р-11). Экрана правки пока нет — План, «Отложено» |

## Как добавить модуль

1. **`app/model.ts`** — типы записей, имена хранилищ в `SYNCED_STORES`, строки в `StoreRecord`, новое значение в `RecordKind`
2. **`app/config.ts`** — строки в `indexes` и `storeNotes`. Для хранилищ после версии 1 `indexes` только держит таблицу полной: индексы заводит миграция
3. **`app/model.ts`** — миграция: поднять `SCHEMA_VERSION`, добавить шаг. Шаг **сам создаёт хранилище и его индексы**; `v1Stores` не трогается никогда. Первая миграция поверх ядра — точка невозврата перевода (Р-49). `additive: true`, если форма прежних записей не меняется. Перед пушем — оба прогона на свежей копии настоящих данных
4. **`modules/<имя>/`** — расчёт, экраны, работа с `db`
5. **`app/config.ts`** — строка в `places`: одним файлом или нарезкой по месяцам, и по какой дате берётся месяц
6. **`app.tsx`** — маршрут, при необходимости вкладка
7. **`src/registry.ts`** — строка на вид записи: подпись, строки ленты, раздел markdown, раздел импорта. Компилятор не соберёт приложение, пока строки нет

Чего делать **не** нужно: править ядро в `src/shared`, сам проход синхронизации или соседний модуль. Понадобилось — граница нарушена, и это повод остановиться.

## Реестр видов записей

Общая лента и выгрузка в markdown — единственные места, где виды записей встречаются по данным. Реестр — таблица `{ [K in RecordKind]: … }` в `src/registry.ts`; тип проверяется компилятором на полноту. Сейчас вид один — `intake`.

- **Учёт в ленте — строка на день**, а не на запись: «Завтрак: каша, компот · Обед: суп…»; под ней — порции дня и ккал с основанием, если известны хоть у одной записи; ищутся ещё категории, группы и заметки дня; тап — день на «Сегодня». Так же, как учёт времени в «Делу Время» (их Р-58). Расчёт — `modules/food/feed.ts`
- **Раздел markdown** — по месяцам, дням и приёмам, за выбранный период: всё время, год или месяц (Р-34). Выбора разделов нет, пока вид один
- **Раздел импорта** — `categories`, `dishes`, `intake`: у вида записи не один раздел, а список, по порядку. Отступление от реестра «Делу Время», где на вид — один раздел: у еды справочники приходят тем же файлом, что и записи
- Реестр растёт по этапам, как у «Делу Время» (их Р-23): с Этапа 1 — подпись и импорт, с Этапа 5 — лента и markdown

Маршруты, вкладки и блоки «Сегодня» через реестр не идут — это продуктовые решения.

## Договор семьи

**Договор живёт в `FamilyCore`** — репозитории общего ядра (Р-50, Р-51). Там он и код, и описание: `Base`, `Migration`, `FeedItem`, раскладка и проверка `schemaVersion` — файлы ядра, а не абзац, повторённый в каждом приложении. Описание — `src/shared/docs/02-Архитектура.md`, «Договор семьи».

Чем «Трапеза» обязана договору:

- **`Base`** — `id`, `updatedAt`, `deleted?` — берётся из ядра, своего не заводится
- **`FeedItem`** — строка ленты `{ kind, id, date, title, detail, link?, extra? }`; собирает её `registry.ts` «Трапезы», форму задаёт ядро
- **Раскладка данных** — `meta.json` со `schemaVersion`, справочники одним файлом, записи — `intake/ГГГГ-ММ.json`; своя таблица мест — в `places` конфига приложения (Р-47)
- **Своя `schemaVersion` и свои миграции** — поля конфига; ядро номера не диктует
- Метаприложение будет читать договорённый срез — строки ленты и итоги, — а не сырые хранилища: миграция «Трапезы» иначе отзовётся в нём

Правка договора — правка ядра, то есть релиз на все приложения сразу (Р-51). Тихо в одном приложении договор не меняется.

**Метаприложение семьи здесь не описывается** (Р-51): «Трапеза» — про еду. Оно только читает остальные (Р-05, Р-06), и его замысел планируется отдельно, когда семья собрана.

## Версионирование схемы

`meta.json` содержит `schemaVersion`. Заводится с первого дня, миграции пишутся сразу: свежая база доезжает до текущей версии теми же шагами, что и база установленной копии. Отставание схемы само по себе не отвергает файл-копию — только если между версиями есть шаг с `additive: false`. Устройство на старой версии, увидев схему новее в репозитории, останавливает синхронизацию со словами «обнови приложение».
